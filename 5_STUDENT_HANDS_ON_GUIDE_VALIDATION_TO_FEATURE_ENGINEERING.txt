====================================================================================================
ABOUT THE VS CODE TERMINAL - ONE CORRECTION
====================================================================================================

Partly correct. The VS Code terminal does NOT make commands OS-independent. It opens your operating
system's default shell - PowerShell on Windows, zsh or bash on macOS.

What is true: every command in this guide that begins with python, pip, feast, dvc, git or
great_expectations is identical on Windows and macOS, because those invoke PROGRAMS, not shell
built-ins. This guide uses almost nothing else, so you can follow it on either OS.

Only four things genuinely differ, and both versions are given at every point in this guide where
they occur:

+-----------------------------+-------------------------------------+----------------------------------+
| TASK                        | WINDOWS (PowerShell)                | macOS / LINUX (zsh, bash)        |
+=============================+=====================================+==================================+
| Create the venv             | python -m venv venv                 | python3 -m venv venv             |
+-----------------------------+-------------------------------------+----------------------------------+
| Activate the venv           | .\venv\Scripts\Activate.ps1         | source venv/bin/activate         |
+-----------------------------+-------------------------------------+----------------------------------+
| Set an environment variable | $env:OPENLINEAGE_DISABLED = "true"  | export OPENLINEAGE_DISABLED=true |
+-----------------------------+-------------------------------------+----------------------------------+
| Open an HTML report         | start <path>                        | open <path>                      |
+-----------------------------+-------------------------------------+----------------------------------+

Everything else in this guide is identical on both.

+--------------------------------------------------------------------------------------------------+
| TIP - ONE IDENTICAL SHELL ON EVERY MACHINE                                                       |
+--------------------------------------------------------------------------------------------------+
| Click the down-arrow next to the terminal + icon, choose Select Default Profile,                 |
| then pick Git Bash on Windows.                                                                   |
| The left-hand column above then works everywhere too.                                            |

PHASE 1 - INPUT DATA
====================================================================================================

Prompt (write this code yourself)
---------------------------------

      Write a Python script that unpacks a bundled zip of raw market data into a
      partitioned folder layout: data/raw/{dataset}/year=YYYY/month=MM/date=YYYY-MM-DD/.
      Datasets: dam, rtm, weather, calendar. Make it idempotent - re-running must not
      duplicate or corrupt existing partitions. Log how many files landed per dataset.

Code elements to study
----------------------

  - How the year= / month= / date= partition path is built from a date string
  - Why partitioning by date matters - it lets every later stage load exactly one day
  - Idempotency: what happens on a second run

Run
---

      python scripts/populate_raw_data.py

Verify
------

      python -c "import glob; print(len(glob.glob('data/processed/**/*.parquet', recursive=True)), 'silver files')"

Review output
-------------

      python -c "import pandas as pd; df=pd.read_parquet('data/processed/dam/year=2025/month=03/date=2025-03-15/part-0001.parquet'); print(df.shape); print(df.columns.tolist()); print(df.head())"

Ask yourself: how many rows for one day of DAM? Does it match 96 blocks?

PHASE 2 - DATA VALIDATION (GREAT EXPECTATIONS)
====================================================================================================

Prompt (write this code yourself)
---------------------------------

      I have daily Parquet files for a market dataset. Using Great Expectations 0.17.22
      (V3 API, RuntimeBatchRequest), write:

      1. An expectation suite as JSON that checks schema, row count, nulls on key columns,
         uniqueness of the natural key, and physically justified numeric ranges.
      2. A script that validates one date, and instead of passing or failing the whole
         batch, SPLITS the rows into valid and invalid - writing each to a separate
         Parquet folder, with the failure reason attached to every invalid row.

      Explain why you chose each numeric bound.

Code elements to study
----------------------

Open src/2_validation/5_gx_validate_local.py and find:

+----------------------------------------------+----------------------------------------------------+
| ELEMENT                                      | WHY IT MATTERS                                     |
+==============================================+====================================================+
| GE_ROOT, LOCAL_SILVER, LOCAL_VALID           | Where GX looks and where output goes               |
+----------------------------------------------+----------------------------------------------------+
| DATASETS dict                                | Which datasets are active                          |
+----------------------------------------------+----------------------------------------------------+
| load_silver()                                | Three different layouts - weather is per-city,     |
|                                              | calendar is one file, the rest are per-date        |
+----------------------------------------------+----------------------------------------------------+
| run_validation() -> result_format="COMPLETE" | THE MOST IMPORTANT LINE. Only COMPLETE returns     |
|                                              | unexpected_index_list. With the default, every row |
|                                              | looks valid                                        |
+----------------------------------------------+----------------------------------------------------+
| unexpected_index_list -> failing_by_row      | How a rule failure becomes a ROW failure           |
+----------------------------------------------+----------------------------------------------------+
| split_rows()                                 | The metadata columns added to each stream          |
+----------------------------------------------+----------------------------------------------------+
| save_parquet()                               | How the output partition path is constructed       |
+----------------------------------------------+----------------------------------------------------+

Also open gx/expectations/weather_suite.json and find the row_condition and mostly rules - the

====================================================================================================
PHASE 3 - FEATURE ENGINEERING
====================================================================================================

Prompt (write this code yourself)
---------------------------------

      I have four validated datasets at different time resolutions: one at 15 minutes,
      one at 30 minutes, one hourly per city (30+ cities), and one daily.

      Write a script that combines them into ONE table at 15-minute resolution, ready
      for a gradient-boosted tree model predicting a price one day ahead.

      Decide and justify:
      - how to align the different granularities without inventing data
      - what encoding each column type needs (cyclical? categorical? high-cardinality?)
      - which lag and rolling features are safe given the one-day horizon
      - what to do with rows where the longest lag is not yet available

      Output a table of every input column and the encoding you chose, before the code.

Code elements to study
----------------------

Open src/3_feature_engineering/1_build_features.py and find:

+----------------------------------------------+----------------------------------------------------+
| ELEMENT                                      | WHY IT MATTERS                                     |
+==============================================+====================================================+
| FEATURE_COLS                                 | The frozen feature contract. Order matters - it    |
|                                              | must match Feast and the serving app               |
+----------------------------------------------+----------------------------------------------------+
| META_COLS                                    | Pipeline columns stripped from every source        |
+----------------------------------------------+----------------------------------------------------+
| clean_market() - the IQR clip                | Outliers are CLIPPED, NOT DROPPED, so the row's    |
|                                              | other features survive                             |
+----------------------------------------------+----------------------------------------------------+
| clean_market() - dedup key                   | RTM dedups on Datetime + session, DAM on Datetime  |
|                                              | alone. Why the difference?                         |
+----------------------------------------------+----------------------------------------------------+
| clean_calendar()                             | Text columns become 0/1 flags. Why not one-hot the |
|                                              | festival names?                                    |
+----------------------------------------------+----------------------------------------------------+
| aggregate_weather()                          | mean for temperature but sum for rainfall. Why?    |
+----------------------------------------------+----------------------------------------------------+
| build_spine()                                | RTM 30 to 15 min and weather hourly to 15 min      |
|                                              | expansion by DUPLICATION, not interpolation        |
+----------------------------------------------+----------------------------------------------------+
| add_features() - sin and cos                 | Cyclical encoding. Why can't hour stay a 0-23      |
|                                              | integer?                                           |
+----------------------------------------------+----------------------------------------------------+
| add_features() - bpd = 96                    | Lags are expressed in BLOCKS, not days             |
+----------------------------------------------+----------------------------------------------------+
| add_features() - .shift(1).rolling(...)      | LEAKAGE GUARD. Trace what happens if you delete    |
|                                              | .shift(1)                                          |
+----------------------------------------------+----------------------------------------------------+
| finalize() - dropna                          | Warm-up rows dropped, not imputed                  |
+----------------------------------------------+----------------------------------------------------+

Run
---

      python src/3_feature_engineering/1_build_features.py --year 2025 --month 3

Verify
------

      python -c "import pandas as pd; df=pd.read_parquet('data/features/march_2025_eda/march_2025_prepared.parquet'); print('shape:', df.shape); print('NaNs:', df.isna().sum().sum())"

Expected: about 2304 rows by 41 columns, and 0 NaNs.

Review output
-------------

      python -c "import pandas as pd; df=pd.read_parquet('data/features/march_2025_eda/march_2025_prepared.parquet'); print(df.columns.tolist()); print(df[['Datetime','dam_mcp','dam_mcp_lag_1d','avg_temp','is_peak_hour']].head())"

Checks you must be able to explain:

  - Why did the row count drop from about 2,976 to about 2,304? (Hint: 7 days x 96 blocks)
  - Confirm dam_mcp_lag_1d at row t equals dam_mcp at row t - 96
  - mcp_spread should hover around zero. A large constant offset means a broken join

====================================================================================================
PHASE 4 - FEATURE STORE (FEAST)
====================================================================================================

Prompt (write this code yourself)
---------------------------------

      I have a feature table with one row per 15-minute block and about 39 columns.
      Write the Feast definitions (Feast 0.61, local provider, file offline store,
      sqlite online store) that:

      - define the time block as the entity
      - split the features into separate feature views by domain instead of one big view
      - bundle them into a single named feature service that training and serving both use

      Explain why splitting by domain matters, and why serving code should reference the
      feature service by name rather than listing columns.

Code elements to study
----------------------

Open my_feature_store/feature_repo/feature_definitions.py and find:

+----------------------------------------------+----------------------------------------------------+
| ELEMENT                                      | WHY IT MATTERS                                     |
+==============================================+====================================================+
| Entity(name="block_id", join_keys=[...])     | The join key that ties a feature row to a moment   |
|                                              | in time                                            |
+----------------------------------------------+----------------------------------------------------+
| FileSource(timestamp_field="event_timestamp") | Feast requires an explicit event-time column       |
+----------------------------------------------+----------------------------------------------------+
| Three FeatureViews                           | Split by domain so each can evolve independently   |
+----------------------------------------------+----------------------------------------------------+
| Field(dtype=Int64) vs Float64                | A wrong dtype produces SILENT NULLS at materialize |
|                                              | time, not an error                                 |
+----------------------------------------------+----------------------------------------------------+
| ttl=timedelta(days=365)                      | How far back a feature stays valid                 |
+----------------------------------------------+----------------------------------------------------+
| FeatureService("dam_mcp_forecast_v1")        | The single source of truth. Add a field to a view  |
|                                              | and it flows everywhere                            |
+----------------------------------------------+----------------------------------------------------+

Also open src/3_feature_engineering/2_prepare_feast_data.py and find where event_timestamp and
block_id are created, and the dedup groupby.

Initialize
----------

The repo already exists. Confirm the config:

      python -c "print(open('my_feature_store/feature_repo/feature_store.yaml').read())"

+--------------------------------------------------------------------------------------------------+
| EVERY FEAST COMMAND MUST RUN FROM THE FOLDER CONTAINING feature_store.yaml                       |
+--------------------------------------------------------------------------------------------------+
| Running it from one level up gives: Can't find feature repo configuration file                   |
| Either cd my_feature_store/feature_repo first, or use the -c flag shown below.                   |
+--------------------------------------------------------------------------------------------------+

Run
---

Identical on both systems - the -c flag points Feast at the repo, so you never have to cd:

      python src/3_feature_engineering/2_prepare_feast_data.py
      feast -c my_feature_store/feature_repo apply
      feast -c my_feature_store/feature_repo materialize-incremental 2025-04-01T00:00:00

The fixed timestamp above works for the March 2025 demo data. To materialize up to RIGHT NOW
instead, the timestamp syntax is the one place the shells differ.

  Windows:

      feast -c my_feature_store\feature_repo materialize-incremental $(Get-Date -Format "yyyy-MM-ddTHH:mm:ss")

  macOS / Linux:

      feast -c my_feature_store/feature_repo materialize-incremental $(date +%Y-%m-%dT%H:%M:%S)

Verify
------

      feast -c my_feature_store/feature_repo entities list
      feast -c my_feature_store/feature_repo feature-views list
      feast -c my_feature_store/feature_repo feature-services list

Review output
-------------

      python src/3_feature_engineering/4_query_online_store.py

Fetch features for one block, exactly as the serving app does:

      python -c "from feast import FeatureStore; s=FeatureStore(repo_path='my_feature_store/feature_repo'); fs=s.get_feature_service('dam_mcp_forecast_v1'); print(s.get_online_features(features=fs, entity_rows=[{'block_id':'2025-03-20T18:00'}]).to_dict())"

+--------------------------------------------------------------------------------------------------+
| WHAT TO CONCLUDE                                                                                 |
+--------------------------------------------------------------------------------------------------+
| feast apply registers WHAT THE FEATURES ARE. feast materialize copies WHAT THE VALUES ARE.       |
| Training and serving both read the same definition - that is what prevents training/serving      |
| skew.                                                                                            |
+--------------------------------------------------------------------------------------------------+
